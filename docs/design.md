# zero-notice：Agent Harness 通知中枢方案与交接

## 当前需求与进度

用户希望做一个能扫描各种 Agent harness 的通知程序，在 Agent 完成任务、等待用户输入、等待权限确认或异常停止时发送通知。用户已经验证 Bark 推送接口可以成功调用。

当前已完成首个 Codex + Bark MVP：使用 Node.js 原生模块实现 `Stop` 完成通知与 `PermissionRequest` 等待确认通知，从项目根目录 `.env` 读取 Key，并提供本地模拟服务测试、持久化去重和 Codex 配置安装脚本。新 handler 已加入 `~/.codex/hooks.json`，仍需用户在 Codex `/hooks` 中审查并信任。Pi、Claude Code 和 OpenCode 适配器尚未实现。

## 产品目标

定位为本机运行的 Agent 通知中枢：自动发现会话，接收各工具的状态事件，将需要用户关注的变化通过 Bark 等渠道推送。

核心价值是识别“什么时候需要用户回来处理”，而非仅识别进程是否存在。例如，Agent 自己能修复的命令失败通常不需要推送，等待用户批准的操作则应该及时通知。

建议架构：

```text
Claude Code / Codex / Pi / 其他 CLI
                 ↓
     适配器：发现会话并获取事件
                 ↓
     统一事件、状态判断、去重与规则
                 ↓
       Bark / 桌面通知 / Webhook
```

## 会话发现与事件来源

将“发现正在运行的工具”和“判断会话状态”分开实现。扫描进程可以辅助定位工具、项目与会话，但不能可靠区分 Agent 正在思考、等待输入或完成任务。

事件接入优先级建议如下：

| 接入方式 | 作用 | 限制 |
| --- | --- | --- |
| 官方 hook / 扩展事件 | 获取任务结束、等待确认等明确事件 | 每种 harness 需要单独适配，并核实版本支持 |
| 会话日志监听 | 支持缺少 hook 的工具、补充会话信息 | 格式可能变化，需处理轮转、半行和历史回放 |
| 进程扫描 | 自动发现运行中的工具，辅助判断异常退出 | 不能单独作为任务状态判断依据 |
| 包装启动命令 | 获取启动参数和退出码，提供基础兼容能力 | 需要用户改变启动方式，交互式工具的退出码不代表每轮任务结果 |

避免第一版依赖终端文本中的“完成”“error”等关键词：误判概率高，终端刷新与工具输出也不适合作为稳定协议。

自动发现不等于自动修改工具配置。安装 hook 或扩展应有明确命令、变更说明和卸载路径；扫描与查看状态不应隐式修改其他工具配置。

## 统一事件模型

首批候选事件：

- `completed`：本轮交互已经结束，可以回来查看结果；不保证整个用户目标已完成。
- `needs_input`：需要用户回答问题或补充信息。
- `approval_required`：等待用户批准权限或操作。
- `failed`：任务无法继续或会话异常停止；普通子命令失败不应直接等同于此事件。

建议事件字段：

```ts
type AgentEvent = {
  id: string;                // 来源提供的事件 ID，或适配器生成的稳定标识
  harness: string;
  sessionId: string;
  projectPath?: string;
  type: 'completed' | 'needs_input' | 'approval_required' | 'failed';
  occurredAt: string;         // ISO 8601
  summary?: string;
  source: 'hook' | 'extension' | 'log' | 'process' | 'wrapper';
};
```

此结构为设计草案，实施时可调整。需要验证各 harness 是否真实提供这些事件；不能从缺失信息中推断一个确定状态，也不能承诺所有工具都支持全部事件类型。

## 通知规则与可靠性

第一版应优先保证准确性和去重：

- 按会话与事件标识去重，持久化必要状态，服务重启后不重复发送已处理事件。
- 初次接入默认从当前时点开始监听，避免重放旧会话并集中推送历史消息。
- 对日志监听保存读取位置，处理文件截断、轮转和尚未完整写入的记录。
- 权限确认和等待输入优先发送；普通完成事件可按会话短时间合并。
- 不把每条日志、每次工具调用或可恢复错误都推送给用户。
- 对会话异常退出的判定留出合理余地，区分正常结束、重启、暂时不可访问等情况。
- 推送失败需要有界重试与可观察的错误记录。网络超时可能发生在服务端已受理之后，重试可能造成重复通知，不能承诺端到端恰好一次送达。
- 默认只发送工具名、项目名、事件类型和简短摘要，不发送完整对话、命令输出、代码或敏感信息。

可选的后续能力：静默时段、仅离开电脑时推送、等待超过指定时长再提醒、桌面通知、多设备配置。

通知示例：

```text
标题：Codex · zero-notice · 等待确认
正文：需要批准运行数据库迁移。已等待 2 分钟。
```

示例内容仅用于说明展示形式；实际摘要必须由事件来源支持，不能凭空生成。

## Bark 渠道

用户已通过 `https://api.day.app/<device-key>/<title>/<body>` 形式验证真实推送，返回 `code: 200` 和 `message: success`。服务端受理不等于设备一定展示通知。

用户此前提供了真实设备 Key。不要把它复制到文档、源码、示例配置或版本库；使用占位符，通过本地配置或环境变量注入，并避免在日志中输出带 Key 的完整 URL。

建议按“工具名 + 项目名”设置 Bark 的 `group`。Bark 请求方式、正文编码、参数支持与 `ttl` 的确切语义应在实施前查阅官方文档核实，不能将前文对 `ttl=600` 的解释作为已验证事实。

仅在用户明确要求测试推送时发送真实通知，常规验证可使用本地模拟服务。

## 第一版建议范围

先实现本地常驻程序、Bark 通道和两个适配器，优先验证完成通知与等待操作通知的准确性。

候选接入为 Pi 与用户最常用的另一个 harness。用户当前在 Pi 环境中，但尚未确认第二个工具，也未确认必须先做 Pi；不要将候选顺序误认为既定要求。

候选 CLI：

```bash
zero-notice start       # 启动监听
zero-notice status      # 查看接入情况和活跃会话
zero-notice doctor      # 检查配置、事件来源和推送连接；默认不发真实通知
zero-notice test        # 用户主动发送测试通知
```

技术栈建议为 TypeScript + Node.js，便于实现 CLI、文件监听与 Pi 扩展。如果单文件分发和后台驻留是首要目标，可评估 Go。当前尚未做最终选择。

建议模块划分：

```text
CLI / 配置
发现与适配器
事件归一化与会话状态
通知规则与去重存储
Bark 通道
运行状态与诊断
```

## 实施顺序与验收

1. 核实目标 harness 的官方事件接口、日志位置和版本差异，列出支持能力；涉及 Pi 时先阅读本机 Pi 文档。
2. 确定一个真实可用的事件来源，打通“事件 → 规则 → Bark 通道”的最小链路。
3. 增加状态持久化、去重、启动时跳过历史和失败处理。
4. 接入第二个 harness，验证统一事件模型是否足够，再完善发现与诊断命令。
5. 提供配置示例、安装/卸载说明和运行方式。

关键验收场景：

- 真实的本轮结束事件产生一次完成通知。
- 明确的等待输入或权限确认事件产生对应通知。
- Agent 可自行恢复的命令错误不会直接触发失败通知。
- 重复事件和通知服务重启不会重放已处理的历史事件。
- 多个项目或会话并行时能够正确归属与分组。
- 推送不可用时能看到原因，重试有界且不会泄露设备 Key。

优先对状态、去重和重启恢复做有意义的自动化测试；Bark 请求使用模拟端点验证。真实设备推送由用户显式触发。
